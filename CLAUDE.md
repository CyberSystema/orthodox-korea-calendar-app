# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Orthodox Korea Calendar — an **Expo (managed workflow) React Native** app showing the Orthodox liturgical calendar (feasts, fasts, readings, saints) plus admin-authored events, in **English and Korean**, for iOS and Android. The backend is a Cloudflare Worker; liturgical day data is pulled from a public GitHub repo. Builds and submissions go through **EAS**.

Stack: Expo SDK 57 / React Native 0.86 / React 19 / TypeScript 7, Zustand (state), React Navigation, i18next, dayjs, react-native-reanimated 4 + react-native-svg.

## Commands

```bash
npm run typecheck            # tsc --noEmit — the primary validation gate (there is no test suite)
npm run format               # prettier --write . (single quotes, printWidth 100)
npm run format:check         # prettier --check . — verify styling
npm run doctor               # npx expo-doctor — checks SDK/dependency health
npm start                    # expo start (Metro)
npm run start:clear          # expo start --clear (reset Metro cache)
npm run ios / npm run android  # local native run (expo run:*) — triggers a prebuild

# Calendar data — single source of truth is public/data/ in the webapp repo
npm run sync:calendar-data   # regenerate the bundled offline seed from the source of truth
npm run check:calendar-data  # fail if the seed has drifted (build:* run this first)

# EAS builds — build numbers are AUTOMATIC and independent of `version`.
# `version` ("1.3") is a human decision in app.json. ios.buildNumber and
# android.versionCode are not: EAS assigns them (appVersionSource "remote" +
# autoIncrement), and local builds derive them from `git rev-list --count HEAD`
# via app.config.js. The values still in app.json are only the fallback used when
# git is unavailable — a builder gets the tree without .git. Do not bump by hand.
npm run build:ios:preview        # → staging backend  (runs check:calendar-data first)
npm run build:ios:production     # → production backend
npm run build:android:preview / :production
npm run submit:ios / submit:android

# OTA updates (JS-only changes, e.g. translations — no store release, no native change)
npm run update:production -- -m "..."   # publish to the production channel (gated by typecheck)
npm run update:preview -- -m "..."      # publish to the preview channel
```

There is **no test runner configured** — `npm run typecheck` is the validation gate after changes.

When invoked from inside Xcode, use the `xcode-tools` MCP `BuildProject` to compile the native iOS app, and `GetBuildLog` (severity `error`) to read failures.

## Architecture (the big picture)

**Boot chain:** `index.ts` → `App.tsx` (imports `react-native-gesture-handler` first) → `src/app/RootApp.tsx`. `RootApp` is the orchestrator: it initializes notifications, hydrates both stores, kicks off calendar-data sync from GitHub, registers the push subscription, wires deep linking, and gates a minimum-duration branded splash (`ByzantineSplashScreen`).

**State — two Zustand stores (no Redux, no Combine/observables):**

- `src/store/useAppStore.ts` — language, hydration flag, and admin/staff auth state. Persisted via `secureStorage`.
- `src/features/events/useEventsStore.ts` — admin-authored custom events and their incremental backend sync (cursor-paged), persisted to secure storage.

**Calendar data has TWO independent sources, merged at read time:**

1. **Liturgical days** (feasts/fasts/readings/tone) — fetched from a public GitHub repo by `src/features/calendar/webCalendarSource.ts`, cached to the device filesystem, loaded per liturgical year.
2. **Events** (admin-created, may recur) — from the Cloudflare backend, synced incrementally into `useEventsStore`.

`src/features/calendar/calendarService.ts` is the read API the screens use. It builds **in-memory indexes** (by-date and by-month, split into public vs. admin-draft) from both sources, expands **recurring events** into bounded occurrence dates (±1 year window, capped), and dedupes. Its index cache invalidates by **reference identity** of `customEvents` — every store mutation must return a _new_ array (it does), so never mutate event arrays in place.

**Backend access is layered — keep the layers separate:**

- `src/services/backend-sdk/` — transport-agnostic API client (`OrthodoxCalendarApiClient`), request/response `contracts`, and token/cursor `stores`. No app-specific assumptions.
- `src/services/api/` — app wiring on top of the SDK: the singleton `backendClient` (`backendClient.ts`), `eventsRepository`, `subscriptions` (push registration), and `adminAuth`. The admin bearer token and sync cursor live in **SecureStore** (Keychain/Keystore), never in plaintext.

**Navigation:** `src/navigation/RootNavigator.tsx` (native-stack) hosts `MainTabs` (Today, Month) plus `EventDetail`, `Settings`, and the hidden `SecretMenu`. Deep links are normalized in `src/services/deepLinking/linking.ts` (custom scheme `okncalendar://` and `applinks:orthodox-korea-calendar.pages.dev`); only those origins are honored.

**Admin / staff (backend-driven, never client-side password checks):**

- The **secret admin console** (`SecretMenuScreen`) is reached by **7 rapid taps on the "ORTHODOX KOREA" brand title** → password prompt → Cloudflare admin login. It includes a backend terminal; destructive commands against `prod` require confirmation.
- **Staff mode** (event editing) is toggled in `Settings`. Auth state persists as a flag + a verified session token only — **never store the raw passcode**.

## Localization

i18next with `en` and `ko` (`src/i18n/locales/`). `src/i18n/index.ts` initializes i18n and registers the dayjs `ko` locale process-wide — **as an import side effect**. `RootApp.tsx` is its only importer (`import '../i18n';`), so deleting that line silently leaves i18next uninitialised and _every_ screen renders raw keys like `nav.today`. `tsc` cannot catch this (the parity guard only checks that keys exist), so verify on a device after touching RootApp's imports. **`en.ts` and `ko.ts` must stay at full key parity** — a referenced key missing from a locale renders the raw key string to users (a release blocker). User-facing strings go through `t()`; the `SecretMenuScreen` admin console is intentionally English-only.

## Config & conventions that bite

- **Environments:** `EXPO_PUBLIC_APP_API_BASE_URL` selects the backend, set per EAS profile in `eas.json` (preview → staging, production → production). `backendClient.ts` falls back to a hardcoded prod URL when unset (and a dev URL under `__DEV__`). `EXPO_PUBLIC_CALENDAR_DATA_BASE_URL` optionally overrides the GitHub data source. **Note:** `eas update` does **not** apply eas.json build-profile `env` — publish OTA via `npm run update:*` (`scripts/publish-update.mjs` reads eas.json and inlines the right `EXPO_PUBLIC_*`), never bare `eas update`, or an OTA would fall back to the hardcoded prod URL (a preview update would repoint staging at production).
- **Calendar data has ONE source of truth: `public/data/` in the webapp repo** (`orthodox-korea-calendar`). That is what GitHub serves at runtime; the app checks it on every startup and migrates changes into its local cache (`webCalendarSource.ts`). The app also bundles an offline first-launch seed under `assets/webapp-source/data/` + `bundledCalendarData.generated.ts` — these are **derived artifacts, never hand-edited**: run `npm run sync:calendar-data` to regenerate them from the source, and `npm run check:calendar-data` (which every `build:*` runs first) fails on drift. Both are gitignored from Prettier so formatting can't diverge them from the source.
- **Prettier** (`.prettierrc`: single quotes, `printWidth` 100): `npm run format` / `format:check`. `.prettierignore` excludes native/generated output and the bundled calendar data. There is **no ESLint**.
- **babel.config.js:** do **not** list `react-native-worklets/plugin` (or the old `react-native-reanimated/plugin`) manually — `babel-preset-expo` (SDK 57) auto-injects it for Reanimated 4. Adding it double-applies the worklets transform.
- **Several packages are deliberately AHEAD of the Expo SDK baseline** and are listed in `expo.install.exclude` in `package.json` (react, react-native, react-native-gesture-handler, react-native-reanimated, react-native-safe-area-context, react-native-svg, react-native-worklets, typescript). Without that list `npx expo install --fix` silently _downgrades_ them to the SDK's pinned versions — which is a real trap, because a downgrade leaves the previously-generated `android/app/build/generated/autolinking/autolinking.cpp` registering component descriptors the older package no longer defines, and the NDK build then fails with e.g. _"unknown type name 'RNSFormSheetHostComponentDescriptor'"_. If you ever do change one of these versions, wipe `android/app/build/generated/autolinking` and `android/app/.cxx` (or just `npx expo prebuild --clean`) before rebuilding.
- **TWO AUDIENCES, one codebase: the store app shows parishioners NOTHING technical; the owner's sideload shows everything.** This is a product rule, not a preference — when adding UI, decide which side it belongs to. User-facing surfaces (Today, Month, News, Settings) carry only what a reader acts on: no backend URLs, no sync state, no build metadata, no jargon. Anything that answers _"what is the app doing right now"_ goes behind **`DIAGNOSTICS_ENABLED`** (`src/config/features.ts`), which is the same `EXPO_PUBLIC_ENABLE_SECRET_MENU` switch as the console — true only in local sideloads, and inlined at build time so those routes are never registered in a store build. `Settings` is preferences only (Text Size, Launch Screen, Notifications) plus two quiet rows: **Parish staff** (always — it is the one door to event editing, deliberately a plain word rather than a hidden gesture so staff can find it) and **Diagnostics** (owner builds only). Staff sign-in, the passcode field and session state live on `StaffScreen`, never in Settings. `DiagnosticsScreen` is English-only for the same reason the admin console is. Layout rule for user-facing screens: one idea per card, `spacing.xl` between cards, and hint text only where it prevents a real question — the UI should breathe rather than look complete.
- **The lockfile must be written by npm 10, because that is what EAS runs — `npm ci` passing locally proves nothing.** EAS builders are **Node 22 / npm 10.9.8**; this machine is on a much newer Node whose **npm 11 dedupes transitive copies npm 10 insists on listing**. The result is a lockfile that installs fine here and fails on the builder with ``npm ci` can only install packages when your package.json and package-lock.json are in sync` / `Missing: react-native-worklets@0.10.3 from lock file` — and it fails only _after_ the queue, so each attempt costs hours (it errored two iOS production builds this way). After ANY dependency change, regenerate with **`npx npm@10 install --package-lock-only`** and commit the lockfile; the result installs under both majors, because npm 11 simply dedupes the extra entries. `npm run check:lockfile` (chained into every `build:*`) runs the real `npm ci --dry-run` under npm 10 and fails in seconds rather than hours. If EAS's builder image ever moves to a new npm, bump `EAS_NPM` in `scripts/check-lockfile.mjs`.
- **patch-package:** patches in `patches/` auto-apply via the `postinstall` hook. We currently patch **(1)** `@react-native/gradle-plugin` (RN ships **Gradle 9.3.1** but its bundled gradle-plugin pins the `foojay-resolver-convention` toolchain plugin at **0.5.0**, which references `JvmVendorSpec.IBM_SEMERU` — a constant **removed in Gradle 9.0** — so the Android build crashes at settings evaluation with _"JvmVendorSpec does not have member field IBM_SEMERU"_; the patch bumps foojay to **1.0.0**, the first Gradle-9-compatible release. The plugin runs inside an _included build_, so it can't be overridden from `android/settings.gradle` or `expo-build-properties` — patch-package is the only durable fix), and **(2)** `react-native` (iOS: Fabric **recycles** a `secureTextEntry` TextInput after iOS Password AutoFill, and the recycled input comes back **frozen / non-editable** until an app background+foreground cycle — facebook/react-native#53050; the patch adds `+ (BOOL)shouldBeRecycled { return NO; }` to `RCTTextInputComponentView.mm` so TextInputs are recreated, not pooled — this is what fixed the secret-console passcode freeze). After `npm install` patches re-apply automatically; if you edit a node_modules source, regenerate with `npx patch-package <pkg> --include '<file-regex>'` (the `--include` filter is required — the iOS xcframework build script, a stray Android `.gradle/` build dir, and react-native's enormous tree would otherwise pollute the patch).
- **Local Android builds need a JDK in the 17–21 range — not the newest JDK.** AGP / RN 0.86's Android build fails on JDK 24+ (the `JdkImageTransform` can't process `android-36/core-for-system-modules.jar`, and JDK 24+ native-access restrictions break `react-native-screens`' CMake). Build with e.g. `JAVA_HOME=/Library/Java/JavaVirtualMachines/temurin-21.jdk/Contents/Home`. A bare `./gradlew` also needs the SDK location via `ANDROID_HOME` or `android/local.properties` (`sdk.dir=…`); Android Studio and EAS set these automatically, and **EAS uses its own correct JDK**, so this only bites local CLI builds. Note the release build type is **debug-signed by default** (Expo prebuild) — configure a real upload keystore or use EAS before uploading to Play.
- **Push is OneSignal, not FCM/APNs — and `expo-notifications` is GONE.** All remote push goes through `react-native-onesignal` + `onesignal-expo-plugin`; the device never registers a token with our backend, and the Worker broadcasts with one REST call. `src/services/notifications/oneSignal.ts` is the only file that imports the SDK. The Android-13 permission trap that used to live here (`getPermissionsAsync()` reports **`denied`**, never `'undetermined'`, before the user has ever chosen — so gating on `undetermined` meant the dialog never appeared) **cannot recur**: OneSignal's permission API is boolean, with no tri-state to mis-gate on. The surviving rule is _gate only on already-granted, never on a state Android cannot report_ — and do not gate on `canRequestPermission()`, which is OneSignal's own SharedPreferences bookkeeping rather than an OS query. Verify the OS-level flags, not just app behaviour: `adb shell dumpsys package <pkg> | grep POST_NOTIFICATIONS` — `USER_SET` appears only once the user has actually answered.
- **Text goes through `components/common/ScaledText`, never `react-native`'s `Text`.** Settings → Text Size is an in-app multiplier (`useAppStore().fontScale`, persisted as `app.fontScale`), and the only way it reaches a screen is that wrapper — `Text.defaultProps` is dead under React 19, style inheritance only flows Text-inside-Text, and `typography.size.*` is snapshotted by `StyleSheet.create` at import time, before SecureStore is readable. Screens just swap the import line; StyleSheets stay as written. `npm run check:scaled-text` (chained into `build:*`/`update:*`) fails the build if a screen imports `Text` from react-native outside the small allowlist. Opt a glyph out with `allowFontScaling={false}` — that suppresses both the OS and the app scale, which is what icon-as-text (`✓`, `‹ ›`, the tab-bar day number) wants. The app scale **multiplies** the OS scale and the product is clamped to `MAX_TOTAL_FONT_SCALE` (1.8) — the ceiling the fixed-geometry parts (month grid, tab bar, date ring) were verified against. Chrome React Navigation draws itself (tab labels, native header title) never reaches the wrapper: those are sized from `useTextScale()` in `MainTabs`/`RootNavigator`.
- **`components/common/SelectableText` renders a DIFFERENT component per platform, on purpose — do not "simplify" it back to one.** It opts the day's content (readings, saints, celebrations — deliberately not the flag badges, headings, or the Pressable event cards) into platform text selection. **Android renders a `Text`**, which already gives word selection, drag handles, and Copy/Share/Select-all plus web search. **iOS renders a read-only multiline `TextInput`**, because `<Text selectable>` there is Copy-only and copies the WHOLE node: `RCTParagraphComponentView.canPerformAction:` answers YES for `copy:` and nothing else, and its `copy:` serialises `NSMakeRange(0, attributedText.length)` (legacy `RCTTextView` is identical, so it is not an old-arch/new-arch question). A non-editable UITextView keeps real selection — RN maps `editable={false}` onto `UITextView.editable` and never touches `selectable` — so iOS gets handles, Copy, Look Up and Translate. Verified on the iOS 27 simulator: selecting one word and copying puts exactly that word on the pasteboard (`xcrun simctl pbpaste booted`), not the whole line. Two things keep the TextInput visually identical to a Text: RN drives `textContainerInset` from the style's own padding and pins `lineFragmentPadding` to 0 (so `padding: 0` adds no inset), and `scrollEnabled={false}` makes it size to content. Both branches go through `ScaledText` — which exports a matching `TextInput` — so Settings → Text Size keeps working. Note the iOS branch needs a plain string for `value`, so it flattens interpolated children (`{labels.tone} {item.tone}` arrives as three children) and falls back to `Text` if it meets an element child, which loses the selection range but never loses content.
- **The bottom toolbar is the PLATFORM'S OWN, and it does not take layout space — every tab screen must reserve it itself.** `MainTabs.tsx` uses `createNativeBottomTabNavigator` from `@react-navigation/bottom-tabs/unstable`: a real `UITabBarController` on iOS (so iOS 26+ Liquid Glass comes for free) and a Material `BottomNavigationView` on Android. Everything above it is still the app's own manuscript chrome — `headerShown` is false and each screen draws its branded ORTHODOX KOREA header, which also carries the Settings entry. The catch: a native bar is not part of the scroll view's safe area. Probed on iOS 27, a tab screen still reports `insets.bottom === 34` (the bare home-indicator inset) even though the capsule floats above it, so content scrolls **under the glass** unless the screen pads for it. That is `useTabContentBottomPadding()` — used by Today, Month and Announcements, and deliberately NOT by the root-stack screens pushed over the tabs (Event detail, Announcement detail, Settings), which have no bar beneath them. Its Android constant (80dp) was **measured** on a Fairphone 5, not assumed, and is added to the inset rather than presumed to contain it so 3-button-navigation devices still clear.
- **iPad does NOT get the bottom toolbar, and that is not fixable — it gets the native header instead.** iPadOS 18+ renders a `UITabBarController`'s bar at the **top** of the window, and no option changes that: `tabBarControllerMode` maps straight to `UITabBarController.mode`, whose values are only `automatic` / `tabBar` / `tabSidebar`, and `tabSidebar` merely adds a sidebar-toggle button beside the same top pill (verified on the iPad Pro 11" simulator, iPadOS 27 — do not re-litigate this). That top bar lands exactly where each screen draws its branded ORTHODOX KOREA band, and the two overlap. So `USES_NATIVE_HEADER` (`src/navigation/nativeHeader.ts`, true only on iPad) makes Today/Month/Announcements skip their own band and hands the title, Settings and Search to the platform header. Each screen sets its own `headerLeft`/`headerRight`/`headerTitle` via `navigation.setOptions` rather than MainTabs doing it, so the handlers — including the 7-tap secret-menu counter on the brand title — stay local to the screen. iPhone and Android are untouched. That constant lives in its own module because the screens need it and MainTabs imports the screens.
- **Tab icons must be supplied per platform, and Android's are DRAWABLE NAMES, not `require()`s.** `tabBarIcon` takes a data object, never a component, and react-navigation maps an `sfSymbol` icon to `undefined` on Android — an SF-Symbol-only config renders nothing there. iOS uses SF Symbols (`1.circle`…`31.circle` keeps the date-ring motif; the Today icon IS the date, kept current across midnight by `useDayOfMonth`). Android uses bitmaps from `npm run sync:tab-icons` (`scripts/generate-tab-icons.mjs`, 33 files, drift-guarded by `check:tab-icons` which `build:android:*` runs). Passing `require(...)` fails **in release only**: `Image.resolveAssetSource()` returns an EMPTY uri, RNScreens' `getIdForResourceType` returns -1 for an empty name, its caller only checks `!= 0`, and you get `android.resource://<pkg>/-1` — labels with no icons. The drawable name (`assets_tabicons_today28`) is derived by the asset pipeline from the file path, so **moving or renaming these files changes the name**; the `require` lists in MainTabs exist purely to keep the files in the bundle. Dev is the mirror image — Metro serves them over HTTP and writes no drawable — hence the `__DEV__` branch. **OTA caveat:** release resolves these from the APK's drawables, so changing an Android tab icon needs a native build; `eas update` cannot add a drawable to an installed APK.
- **A fixed-size box around scaling text is the layout bug to look for.** Every Easy-Mode/large-font breakage in this app has been one of two shapes: (1) a `<Text>` with no `flexShrink` between fixed-size siblings — RN defaults `flexShrink` to **0**, unlike the web, so the text never shrinks and instead pushes its neighbours out of a rounded/`overflow: hidden` container where they are clipped (this was the "displaced arrows" report); and (2) a `<View>` wrapper around a `flexShrink: 1` Text that has no shrink of its own, which makes the child's shrink inert. Give growing text `flexShrink: 1`, give fixed chrome `flexShrink: 0`, and size any box that must contain growing type from `useTextScale()` (see the date ring in `LiturgicalDayPanel`). Also note Android under-measures a `<Text>` that carries its own padding/border inside a `flexWrap` row — wrap the chrome in a `<View>` (see `readingTag`).
- **A "hung" Android build is almost always a Metaspace OOM.** If `sideload:android` sits with every Gradle worker at 0% CPU and nothing written to `android/app/build`, it is not compiling — the daemon died on `e: [ksp] java.lang.OutOfMemoryError: Metaspace` and wedged, so the CLI waits forever instead of failing. Confirm with `tail ~/.gradle/daemon/*/daemon-*.out.log`. `plugins/withAndroidBuildMemory.js` raises `org.gradle.jvmargs` (Metaspace 512m → 2048m) and gives the Kotlin daemon its own `kotlin.daemon.jvmargs`; don't lower these — KSP across the Expo modules with `parallel=true` and four ABIs needs the headroom. To recover from a wedged daemon: `pkill -9 -f gradle`. Note `expo run:android --device` matches on device **name** (e.g. `FP5`), not the adb serial.
- **UIScene lifecycle (iOS):** Expo SDK 57's template still starts React Native from `AppDelegate.didFinishLaunchingWithOptions` and ships no UIScene support, but the current iOS SDK _requires_ UIScene adoption (Apple TN3187) or the app fails to launch. The local config plugin `plugins/withIosSceneLifecycle.js` injects both halves together on every prebuild — the `UIApplicationSceneManifest` (Info.plist) **and** a `SceneDelegate` in `AppDelegate.swift` that starts RN in the scene's window and forwards deep links to the existing AppDelegate handlers. Keep them in that one plugin; never add the scene manifest to `app.json` alone (an orphaned manifest pointing at a missing `SceneDelegate` class breaks launch). If the Expo template's RN-startup block changes, the plugin throws a clear error to update it.
- **The Android icon is DERIVED from the iOS icon — never hand-edit it.** `assets/icon.png` is the source of truth; `npm run sync:android-icon` generates `assets/android-icon-background.png` (+ the empty foreground) from it, and `check:android-icon` (run by `build:android:*`) fails on drift. Why it isn't just the same file: an adaptive icon only shows the central 72dp of a 108dp layer, so dropping the iOS artwork in unchanged renders it **1.5× zoomed** (the emblem went 49.8% → 74.7%). The generator scales the artwork to that visible 66.7% and radially bleeds its edge outward to fill the rest, so nothing is cropped and the iOS file's light padding corners can never appear under a squircle mask. All artwork lives in the **background** layer with an intentionally empty foreground — splitting the emblem out would make a launcher's parallax visibly separate it from its background. `android-icon-foreground.png` is still used by the Android splash, so it is left alone.
- **Android must launch into a bare colour too — via a TRANSPARENT splash icon.** Android 12+ renders `windowSplashScreenAnimatedIcon` before JS runs (the theme also sets `windowSplashScreenBehavior=icon_preferred`), so pointing it at the brand mark made Android show a logo first and then the animation — unlike iOS. The icon can't simply be omitted: `withAndroidSplashStyles` always writes that theme attribute, so with no image the drawable is missing and the release build fails at `processReleaseResources`. The fix is `expo-splash-screen`'s `android.image` → `./assets/android-icon-empty.png` (fully transparent): the drawable exists so the build passes, but nothing renders and only the solid `#3A0A0A` shows. Verified by frame-stepping a screen recording — solid colour for ~0.7s, then the animation, no logo. Don't point this back at a logo.
- **Splash screen is two layers — keep them visually matched.** iOS always shows a mandatory native launch splash _before_ JS runs, then the React-Native `ByzantineSplashScreen` (`src/components/common/`) animates once the bundle loads. To avoid a jarring two-screen effect, the native splash is intentionally a **bare solid background with no logo** (`expo-splash-screen` configured with only `backgroundColor: "#3A0A0A"`, which equals `colors.primaryDeep` — the animated splash's opening color), so it blends straight into the animated one. Don't re-add an `image` to the splash plugin (that brings back the static centered-icon screen). The native splash lingers longer in Debug (waiting on Metro) than in Release (embedded bundle).
- **Native `ios/` and `android/` are gitignored generated output** (Expo prebuild). EAS regenerates them on remote builds; for a clean local native build run `npx expo prebuild --clean`. Avoid hand-editing files under `ios/` — changes are lost on the next prebuild (use config plugins / `app.json` instead).
- **A foreground push needs `event.notification.display()` — registering the listener is what breaks it.** `OneSignal.Notifications.addEventListener('foregroundWillDisplay', ...)` is NOT passive: it calls the native `addNotificationForegroundLifecycleListener`, which puts the SDK into lifecycle mode and HOLDS the notification pending an explicit decision from JS. A handler that does side work and returns drops it silently — the push is delivered, OneSignal's dashboard reports it Delivered, and nothing appears on screen. Isolated on device with one variable: same sender (the OneSignal dashboard), same phone, app foregrounded → nothing; app backgrounded → normal. The trap is that backgrounded delivery is unaffected, so a foreground-only bug is invisible unless you test with the app open, and the owner console sends test pushes _from the foreground_ — which made every self-test look like a backend failure. It cost two wrong diagnoses (empty audience, then wrong segment name). If the foreground resync in `oneSignal.ts` is ever removed, remove the listener with it rather than leaving an empty one.
- **There are no Firebase config files any more, on either platform.** OneSignal's Android SDK builds its OWN named `FirebaseApp` (`ONESIGNAL_SDK_FCM_APP_NAME`) from config it fetches at runtime keyed off the OneSignal App ID, so the app needs **no `google-services.json`, no `GoogleService-Info.plist`, and no `com.google.gms.google-services` Gradle plugin** — verified by prebuilding and grepping the generated `android/app/build.gradle`. The FCM service-account JSON and the APNs `.p8` are uploaded to the **OneSignal dashboard** instead. This also retired the `GOOGLE_SERVICES_JSON` EAS file env var and the `firebase()` transform in `app.config.js`, which used to read `process.env` and was therefore a quiet source of fingerprint nondeterminism. **Every `onesignal-expo-plugin` option in `app.json` must stay a literal** for the same reason (`runtimeVersion` is fingerprint-based; an env-driven value diverges between an EAS builder and the machine publishing an OTA, and the update then lands on a runtime no binary matches — silently). The plugin also **rejects unknown props outright, including the `"//"` comment key** used elsewhere in `app.json`, which is why its rationale lives in `app.config.js`. It sits at index 1, not 0: OneSignal's docs say "first" without a reason, `withSolidLaunchScreen` has a documented one, and with `disableNSE: true` there is zero key overlap between them.
- Prefer Swift `async/await`-style APIs over Combine, and React `async`/`await` over RxJS-style observables, consistent with the existing code.
